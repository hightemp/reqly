# ADR-004: Идентификаторы, версии, soft delete и порядок элементов

- Статус: принято
- Дата: 2026-10-17

## Контекст

Этапы 7 (совместная работа) и 10 (синхронизация) требуют, чтобы сущности
можно было создавать офлайн на разных клиентах, сравнивать по версиям и
переупорядочивать без конфликтов. Менять модель данных задним числом дорого.

## Решение

Все синхронизируемые сущности содержат `Meta` (`reqly-core::meta`):

- `id`: **UUIDv7**. Генерируется на клиенте, глобально уникален, упорядочен по времени
  (это хорошо для индексов SQLite).
- `created_at` / `updated_at`: миллисекунды Unix (UTC), берутся из `Clock`
  (в тестах используется `FixedClock`).
- `version`: монотонный счётчик изменений сущности. Растёт при каждом
  изменении, включая удаление и восстановление.
- `deleted_at`: soft delete (корзина, синхронизация удалений).
- `sort_key`: **fractional index** (`reqly-core::sort_key`). Строка base-62 без
  завершающего нуля, сравнивается побайтно. Между любыми двумя ключами всегда
  можно создать новый, поэтому перемещение элемента меняет только его
  собственную запись.
  - Вставка в конец или начало списка увеличивает или уменьшает последнюю цифру
    (длина растёт примерно на 1 символ на 60 вставок).
  - Вставка между двумя ключами берёт середину.
  - `n_between` распределяет групповую вставку равномерно (используется при
    групповом DnD).

## Последствия

- Перемещение в дереве — это `O(1)` записей, без перенумерации соседей.
- Одновременные вставки на двух клиентах в одно место могут дать одинаковый
  ключ. Порядок тогда определяется по `id`, а при синхронизации ключ
  перегенерируется.
- Ключи могут постепенно удлиняться. При необходимости коллекцию можно
  «уплотнить» (перегенерировать ключи); это отдельная операция с инкрементом версий.
